# DiagGraph 助手首版使用说明

本版新增独立接口 `POST /assistant/query`，实现 LLM 五策略路由、可追溯证据 Adapter、证据评价、有界补查询、带来源回答及一次答案修订。管理端和用户端网页聊天现已默认接入助手流程，原 `/query`、`/query/data` 接口保持原有行为；页面的“检索问答”选项保留旧查询方式。

## 1. 已实现的流程

当前问题/用户历史 → 明确风险检查 → LLM 结构化路由并补全当前问题 → 程序校验 → 直接回应/追问/升级，或 mix 检索 → 证据评价 → 若缺用户观察则立即追问，若只缺手册知识则有界补查询 → 基于同一批已接纳证据生成 → 答案核验 → 带引用回答。当前提示版本为 `diaggraph-assistant-v1.4`。

五种路由动作分别为 direct、retrieve_once、diagnose、clarify、escalate。A/B/C 从前三种动作派生，追问与升级没有复杂度标签。diagnose 仅表示需要更复杂的处理流程，不表示已经确诊。

路由以当前消息的意图为准，历史用于补充相关上下文。问完 L4263 墨水编号后单独发送“你好”，应走 general_chat + direct，不继续检索旧问题；直接回复时可省略无关的历史型号，提供的上下文仍须通过原话和型号一致性校验。设备检索仍要求保留最近明确型号。模型若把 general_chat 或纯文本转换分配给检索策略，会在原有两次调用预算内收到纠正反馈，持续无效则明确失败。

路由同一次调用通过 `route.resolved_query` 补全本轮需要检索的问题（最多 2000 字符），不新增独立改写调用。例如用户在喷嘴检查和墨水液位追问后说“怎么进行检查”，应补全为“L4263 如何执行喷嘴检查并查看墨仓中的墨水液位？”。首轮检索使用补全问题，再附加已确认用户事实；补查词仍由证据评价提出。含历史的检索路由若未提供补全问题，会要求模型在原有两次预算内修正，而非默默检索孤立短句。无历史的调用和替换后端仍可省略该字段并使用原问题。补全问题必须保留已提取的设备型号；原始 `request.query/history` 仍保留，评价和生成通过 `current_question` 获取当前目标。

助手历史可用于理解“检查”“这个”等指代，不能成为用户已完成某操作或观察到某结果的证明；`extracted_context` 仍只接受可核验的用户原话。操作方法提问应先查方法，评价不能仅因尚无检查结果而判定无法介绍步骤；会影响安全或路径选择的必要前提仍须保留。是否准确补全语义仍取决于模型，需要真实多轮验证。

独立的“请你再生成一遍”“重新回答一次”“换个说法”等指令会生成 `conversation_context`，指向最近完整的用户/助手回合，跳过中间独立的重复生成回合；若没有可用历史，要求明确重答目标。它只提供动作和消息索引，不把旧助手内容变成事实。旧回答含引用标记时，程序要求重新检索核验，不允许当作 direct 文本改写；引用标记仅作为重查提示，不能证明旧内容正确。路由模型仍须结合此前用户事实补全原问题（如型号来自“L4263”、症状和清洗次数来自更早消息），再走原五策略。普通问候可直接重答。带新型号或新观察的复合请求不会被独立指令匹配吞掉，仍由模型完整理解。当前 HTTP 接口没有可信的上一轮证据会话缓存，不能把浏览器发来的旧回答/引用当成可直接复用的证据。

路由和评价均使用现有 query 角色 LLM，服务调用时解析当前角色配置。当前本地 `.env` 已按用户要求设置 `QUERY_OPENAI_LLM_EXTRA_BODY='{"enable_thinking": false}'`，明确请求 Qwen 服务关闭思考；重启后端后生效。该设置作用于整个 query 角色，包含助手路由、证据评价、回答生成、答案核验及原查询回答。未切换模型或新增训练模型。SDK 可单独注入异步 LLM 调用和 RouterBackend。HTTP 端首版尚无单独的 router 环境变量，不能在页面里假设存在此配置项。

## 2. 启用与调用

代码更新后，由用户按原方式重新启动后端，使新接口加载。默认本地地址为 `http://127.0.0.1:9621`，若配置了反向代理路径前缀，使用相同前缀。鉴权与现有查询接口一致，沿用 API Key 或 Bearer token；不是另一个公开免鉴权入口。

前端接入已构建到 `lightrag/api/webui/`。刷新现有页面（必要时 Ctrl+F5），在用户端 `/workspace/` 或管理端 `/webui/` 的聊天页选择默认的“助手对话”即可使用。助手对话自动携带本入口之前的助手对话历史；与“检索问答”共享可见记录，但不会将旧查询的调试输出、失败或中止的回复作为助手历史。两个入口的记录仍各自隔离。历史最多保留最近 16 个完整回合，并遵守服务端单条/合计字符预算；因长度舍弃上下文时页面会提示，不截断用户事实。

助手当前为非流式接口，等待时只显示等待提示和计时，不编造后台阶段；收到结果后显示回答或追问、业务状态及可展开的引用原文。HTTP 200 内的 failed 会按失败展示，不发布候选答案。停止会取消浏览器请求，晚到的结果不能覆盖清空或新对话；不能据此保证模型服务端已经停止计费。登录、API Key、反向代理前缀沿用原客户端；开发模式代理也已加入 `/assistant`。旧查询的模式前缀、流式、参数面板只在“检索问答”中生效。

引用按最终证据组编号。同一 PDF 的不同引用分别显示文件名、主父块的章节路径和来源页码（连续页合并为范围，保留不连续页的间隔）；展开可查看本次实际证据原文和单独标注的相关前置章节。页码来自已保存的来源元数据，可能与手册印刷页码不同；不据此声称某一句位于范围中的某一页。前端只保留可读章节/页码及原文，不复制完整内部索引字段。刷新后保留新引用的信息；旧聊天记录若此前没有保存章节/页码，显示未提供，不自动重新检索或推测补齐。

下面命令会调用真实模型，由用户自行执行：

```powershell
$headers = @{}
if ($env:LIGHTRAG_API_KEY) {
  $headers['X-API-Key'] = $env:LIGHTRAG_API_KEY
}
$payload = @{
  query = 'L4263 应该使用什么墨水编号？'
  history = @()
} | ConvertTo-Json -Depth 6
$result = Invoke-RestMethod `
  -Uri 'http://127.0.0.1:9621/assistant/query' `
  -Method Post -Headers $headers `
  -ContentType 'application/json; charset=utf-8' `
  -Body ([System.Text.Encoding]::UTF8.GetBytes($payload))
$result.status
$result.route
$result.answer
$result.citations
```

只有 shell 中已经设置 API Key 环境变量时，上例才会附带该请求头；`.env` 不会自动变成 PowerShell 环境变量。登录模式可沿用已有登录得到的令牌添加 Authorization 头，不要把密钥或令牌写入脚本、日志或 Git。

多轮请求是无状态的：每次发送必要历史，包含 role=user/assistant 和 content。例如先说“我的设备是 L3251”，下一轮问“清洗之后还是白纸怎么办”，应把先前用户陈述放进 history。服务不创建会话数据库，也不按客户端身份保存永久设备状态。

请求字段仅有 query 和 history；不接受 mode、任意系统提示、客户端预算或工具权限覆盖。query 最多 8192 字符、history 最多 32 条、每条最多 4096 字符，序列化后合计最多 24000 字符；空白请求和 system 角色历史会被拒绝。

## 3. 返回状态与引用

| status | 含义 |
| --- | --- |
| answered | 首版程序和 LLM 评价均通过，返回回答与实际引用来源 |
| needs_clarification | 需要用户补充会改变处理结果的信息 |
| escalated | 给出专业售后/人工处理建议；没有实际转接或创建工单 |
| insufficient_evidence | 在允许预算内没有形成受支持的答案，未发布候选草稿 |
| failed | 模型、来源、格式、预算、审计或执行错误；查看 error.code 和 error.stage |

通过鉴权且请求格式有效后，业务结果使用结构化响应；HTTP 200 不代表回答成功。必须检查 status。请求校验和鉴权仍通过正常 HTTP 422/401/403 等状态返回。

回答中的 `[1]` 等编号由程序从已引用的真实 evidence_id 生成。citations 给出 document/chunk 来源和文件名，evidence 保留实际返回正文、支持子块集合、父块/前置父块元数据和原始引用编号。父块展开文本不会被源子块正文替换，跨查询不按临时引用编号去重。

metadata 保留路由后端、提示版本、query 或 injected 模型来源、可用的模型名/绑定、原始/最终策略、覆盖原因、各次检索及重排/预算元数据、证据和答案评价、调用阶段与耗时。model_attempts 包括排队尝试，model_calls 只计进入业务模型调用的次数；失败的检索尝试也保留。provider 自身 HTTP 重试、缓存、token 和费用没有统一返回时保持 unknown/null，不捏造实际成本。

`metadata.evidence_selection` 按轮记录考虑组数、实际送入评价的 evidence_id、因预算省略的 ID 和模型证据 token 数。顶层 `omitted_evidence_ids` 是各轮历史省略 ID 的并集，不表示该证据以后仍未被接纳。

## 4. 预算与失败行为

- 路由阶段默认总计 60 秒，证据评价、生成、答案评价等每个模型阶段也默认 60 秒。每个结构化模型阶段最多 2 次业务层调用，格式修复与暂时故障重试共用该阶段的时间与次数上限。不会从坏 JSON 中截取对象、补字段或接纳被截断响应。
- 整个请求默认 300 秒，包含排队、检索、重排、生成及评价；外部取消继续传播。共享模型调用并发默认最多 2，仍受现有 query 角色队列约束。
- retrieve_once 只执行一次 mix；diagnose 最多两轮、三次检索，第一轮充分即可停止，第二轮最多两个缺口查询。
- 证据评价需要用户补充时，`clarification_question` 优先于补查，立即返回 `needs_clarification`；手册无法回答条纹实际方向或用户是否做过某项检查。`followup_queries` 只用于查操作步骤、条件和限制。窄范围规则拒绝明显的用户观察问题被用作检索，以及已从用户原话确认的清洗/重启等次数被重复追问；违反时使用既有阶段内修正次数，不默默删除问题或猜测用户答案。这些规则不是完整的自然语言语义判别器，未覆盖的表达仍需真实验证。
- 合并后的模型证据默认最多 8000 tokenizer token，完整证据组放不下时省略并记录。模型输入移除源定位坐标、跨度和索引 token 计数，保留原文、全部支持子块 ID、分开的父/子适用范围、条件及注释；HTTP evidence 和最终引用仍保留完整归属。补查轮先保留上一轮接纳的证据，再考虑本轮结果，最后考虑旧的未接纳证据，避免旧结果仅凭插入顺序挤掉补查结果。每次模型输入另有 16000 token 上限。
- 生成与答案评价使用同一批接纳证据。评价要求修订时最多再生成一次并复核，仍不通过则不发布草稿。
- 来源缺失、所有权冲突、前置父块归属不完整是 failed，不能当作普通“无相关资料”吞掉。

不同 provider 的自身超时/重试仍由其配置控制；业务层截止时间负责停止等待，不能据此承诺远端已取消计费或 provider 内部恰好只有两次 HTTP 请求。

首次真实请求使用 Qwen3.5-Plus 时，在旧的 15 秒路由截止时间触发 `model_timeout`，尚未开始检索。因此将默认预算放宽到上述值；这只是等待上限调整，不代表已验证模型可用或答案正确。更新代码后需要重新启动后端，再用原请求测试；无需修改请求体或重新构建知识库。若仍超时，结合 `error.stage`、`metadata.model_trace` 与服务端日志检查模型服务、排队和网络耗时。SDK 可通过 `AssistantConfig` 覆盖预算，HTTP 请求体不接收这些参数。

## 5. SDK 与受控审计

已有正确配置的 rag 实例必须先执行 `await rag.initialize_storages()`。随后可用：

```python
from lightrag.assistant import AssistantRequest, AssistantService

assistant = AssistantService(rag)
response = await assistant.run(
    AssistantRequest(query="L4263 的墨水编号是什么？")
)
print(response.status)
print(response.answer)
```

若要单独使用路由/生成模型，可向 AssistantService 的 llm 参数传入兼容 `await llm(prompt, system_prompt=..., stream=False)` 的异步函数；这一首版注入供各助手模型阶段共用，尚未提供每个阶段独立模型选择。router_factory 可注入统一 decide 接口，但来源与风险规则仍在执行边界校验。

HTTP 默认只返回模型调用摘要及响应指纹，不返回原始坏 JSON、被拒绝草稿或完整模型响应，避免将拒绝的候选内容作为最终结果发布。SDK 可通过 audit_sink 注入异步持久化回调，接收完整模型轨迹；由调用方选择受控目录和访问权限，不默认把用户对话存到公共日志。配置了审计回调而写入失败时，结果为 audit_write_failed，不能谎报完整留档成功。

业务失败会记录 warning，包含错误代码、阶段、路由策略、输入指纹和模型错误摘要；不记录用户原文、模型原始响应或供应商异常正文。格式失败的 `model_trace.validation_phase` 区分响应约定、JSON 解析、schema 校验和语义校验，便于区分 HTTP 200 内的实际失败。

每次正常进入助手编排的请求还记录结束摘要，包含业务状态、策略、模型调用数、检索次数和输入指纹。`metadata.termination_reason` 区分 `evidence_insufficient`（证据不足）与 `answer_revision_exhausted`（答案修订后仍未通过），避免把两种相同前端提示误认为同一原因；`metadata.conversation_context` 记录本轮对话动作及目标索引，不记录额外会话原文。
