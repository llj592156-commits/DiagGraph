# DiagGraph 后续小模型路由训练预研

日期：2026-10-18。状态：训练阶段预研，暂缓实施。

**用户最新决定：首版先由高能力 LLM 判断路由，独立训练小模型在后续接入。现行方案见 [首版 LLM 路由设计](AdaptiveRouterDesign-zh.md)。下文保留调整前的训练方案供后续参考；其中“首版”“先训练”“下一次代码开发”等措辞均指旧训练阶段规划，不再是当前执行顺序。15 条样例仍是人工候选，不可直接训练。**

尚未实现 Adapter、路由分类器或训练闭环。下文模型、数据规模、预算和验收数值均为训练阶段候选，不是已经取得的效果；其中路由 2 秒目标不适用于当前首版 LLM 路由。

## 1. 本轮结论与当前起点

采用训练的小模型预测检索复杂度，保留五种业务处理策略。先建立可独立执行的固定路线和可信标签，再训练分类器，不让大模型提示分类成为最终路由实现。

首版约定：

- 分类器输出 A / B / C，分别表示无需检索、单步检索、多步检索。
- 外部业务动作仍为 direct / retrieve_once / diagnose / clarify / escalate。
- 追问和升级由信息检查及安全控制衔接，不强行并入复杂度三分类。
- 需要检索时首版固定使用 mix；分类器暂不预测 naive / hybrid / mix。
- 型号/场景硬过滤、故障码精确或词法召回仍按用户要求暂缓。
- 不增加新知识库，不重新解析或抽取手册，真实付费实验由用户执行。

起点已更新：本地补抽报告 `outputs/printer_skipped_repair/saved_children_v1/summary.json` 记录 targeted_chunks=10、repaired_chunks=10、remaining_skipped_chunks=0。报告接纳 63 个实体记录和 28 个关系记录，包含合并，不代表图中净增数量或语义准确率。旧 90 次检索结果来自补抽前，不能冒充新知识库的路由或答案测试结果。

## 2. 从论文和官方代码确认的事实

主要来源是 [Adaptive-RAG 论文](https://aclanthology.org/2024.naacl-long.389.pdf) 的 3.1、3.2、4.4 节，以及 [官方代码](https://github.com/starsuzi/Adaptive-RAG)。代码核对版本固定为 `0c88670af8707667eb5c1163151bb5ce61b14acb`。这是方法迁移，不宣称完整复现原论文实验。

| 核对项 | 官方实现中的行为 | 本项目的处理 |
| --- | --- | --- |
| 三条路线 | 不检索、单步检索、迭代检索；多步实验使用 IRCoT | 复用 LightRAG；以有界、证据驱动的补查询实现多步，不照搬 IRCoT |
| 分类器 | T5-Large，问题作为输入，A/B/C 作为文本目标 | 首选中文可用的 mT5-small，仍训练标签输出 |
| 结果标签 | 三条路线中正确的较简单路线优先 | 使用通过业务验收的最小路线，而非单看答案字符串 |
| 补充标签 | 单跳/多跳数据集提供 B/C 先验，与结果标签合并 | 使用人工证据需求先验，标明弱标签，不能冒充实测结果 |
| 校验方式 | 官方复杂度结果文件只收录规范化答案精确匹配的题目 | 诊断建议检查来源、适用性和条件，精确匹配仅辅助事实题 |

可定位的代码证据：

- [evaluate.py](https://github.com/starsuzi/Adaptive-RAG/blob/0c88670af8707667eb5c1163151bb5ce61b14acb/evaluate.py#L639)：生成各路线答对问题的记录。
- [preprocess_utils.py](https://github.com/starsuzi/Adaptive-RAG/blob/0c88670af8707667eb5c1163151bb5ce61b14acb/classifier/preprocess/preprocess_utils.py#L129)：先写 C，再由 B、A 覆盖，落实简单路线优先；全部未答对的题不生成这类标签。
- [preprocess_binary_train.py](https://github.com/starsuzi/Adaptive-RAG/blob/0c88670af8707667eb5c1163151bb5ce61b14acb/classifier/preprocess/preprocess_binary_train.py)、[concat_and_save_binary_silver](https://github.com/starsuzi/Adaptive-RAG/blob/0c88670af8707667eb5c1163151bb5ce61b14acb/classifier/preprocess/preprocess_utils.py#L36)：构造 B/C 先验，合并时按 ID 排除与结果标签重复的先验。
- [classifier/utils.py](https://github.com/starsuzi/Adaptive-RAG/blob/0c88670af8707667eb5c1163151bb5ce61b14acb/classifier/utils.py#L79)、[run_classifier.py](https://github.com/starsuzi/Adaptive-RAG/blob/0c88670af8707667eb5c1163151bb5ce61b14acb/classifier/run_classifier.py)：序列到序列训练；推理比较首个输出位置的 A/B/C 分数。
- [训练脚本](https://github.com/starsuzi/Adaptive-RAG/blob/0c88670af8707667eb5c1163151bb5ce61b14acb/classifier/run/run_large_train_xl.sh)：学习率 3e-5、输入长度 384、训练 batch 32，遍历 15/20/25/30/35 epoch。这是已发布脚本配置，不据此声称与论文文字中的所有训练设置完全一致，也不照搬到本地硬件。

官方 README 明示其 silver validation 来自 QA test 预测，训练脚本使用它校验不同 epoch。本项目将独立划分训练、验证、盲测，不使用最终盲测选择参数。

## 3. 业务动作与复杂度标签的边界

| 外部动作 | 复杂度标签 | 条件和边界 |
| --- | --- | --- |
| direct | A | 首版仅允许交流、功能介绍、用户明确提供文本的纯整理；不输出新增设备事实 |
| retrieve_once | B | 用户信息足以检索，先执行一次完整 mix 查询 |
| diagnose | C | 预计需要依据首轮证据补查询；进入此路线不保证必须用完预算 |
| clarify | 无 | 缺失信息确实会改变资料对象或建议；针对缺口追问 |
| escalate | 无 | 明确高风险或确需人工权限；输出升级建议，不假装已创建工单 |

设备操作、耗材、故障码、保修政策等企业或设备事实必须有来源。即使无检索模型碰巧答对，也不能据此把这类问题标成 A；记录原始实验结果和业务规则覆盖原因。这是有意偏离开放域 QA 的业务要求。

三条路线都失败时，记录 unresolved，检查知识缺失、召回缺失、范围不明、生成错误或评审分歧。不能自动贴 C；知识库没有订单和保修状态时，多检索几次也不会得到真实订单。

策略 C 表示检索计划复杂度，不是“已经确诊”。型号数量、文字长度、出现故障码都不能单独决定 C。同一个问题若单次检索已取得充分证据，应优先标 B，即使其人工先验为 C。

## 4. 在线决策与会话输入

流程：当前问题与可追溯会话状态 → 风险/信息检查 → 若无需追问或升级则由小模型预测 A/B/C → 业务规则校验 → 执行固定路线 → 证据与答案检查 → 回答、追问或升级。

首版输入序列化应包含固定字段：当前问题、已确认型号、故障码及出现位置、症状、用户已执行操作、未解决问题。字段为空时保持未知。记录用户明确陈述、历史继承和未知的区别，不把模型推断当成已确认事实。

例如上一轮确认 L3251，本轮说“清洗之后还是白纸”，输入应保留型号和已执行清洗。若用户说“现在换成 L4263”，更新当前设备并保留变更来源，不能沿用旧型号。

不输入检索正文、参考答案、来源文件名暗示、评审结论或路线实测结果。它们只可用于离线标注，不能泄漏给在线复杂度分类器。诊断会话全部轮次和同义变体进入同一个数据划分。

信息提取与复杂度预测是两个任务：三分类模型不会自动补齐型号和历史状态。首版先做明确型号/故障码的保守提取和结构化会话状态；涉及隐含操作或歧义时可以受控使用现有 LLM 提取，须单独计入调用成本。此提取调用不代替训练好的路由模型，也不直接生成最终策略。

复杂度模型返回标签、三类分数、模型版本、输入版本、分数是否校准，以及静态标签说明。静态说明如“模型预测需要多步检索”，不能伪装成模型给出的详细推理。分数不是答案置信度。

低置信度、分布外输入、模型不可用必须有显式状态。需要设备事实的问题绝不降级为 direct；信息齐全时可标记 degraded 并采用单步 mix，再由证据检查决定是否需要有界补查；信息不明则追问。此后备路线单独统计，不能算作模型路由成功。

风险规则不是完整安全保证，混合危险和普通任务时先处理危险；证据审查和最终输出仍保留独立检查。首版规则的覆盖范围、漏报及误报都需要样例验证。

## 5. 固定执行路线与预算

先实现和评测路线，再训练预测其收益的分类器。B/C 使用同一知识库、模型、首轮 QueryParam、证据预算和来源规则；C 的不同点是允许依据证据缺口补查询。所有配置均版本化。

| 路线 | 固定执行定义 | 首版预算建议 |
| --- | --- | --- |
| A | 无知识库查询；仅处理允许的直接回应 | 0 次检索，模板或一次回答调用 |
| B | 一次 mix 结构化检索，评价后用同一批证据回答 | 1 次检索；不足时诚实说明或追问，不偷偷补检索 |
| C | 一次 mix 检索，基于已知证据缺口生成补查询，合并去重再回答 | 至多 2 轮、3 次检索；首轮 1 次，第二轮最多 2 个子查询 |

参数候选沿用当前基线：top_k=20、chunk_top_k=5、rerank_candidate_k=20、实体/关系预算各 2000、最终总上下文候选预算 8000。最终 Generator 模板也要计入预算，不能认为 SDK 的上下文预算天然适合另一个生成模板。

C 可以首轮证据充分便停止，不固定拆成四问。第二轮只补缺口，不反复改写同一问题，累计证据进入最终总预算。总超时、各模型超时和重试上限需作为配置明确记录；建议初版路由 2 秒、请求总计 120 秒、答案修订最多 1 次，均待服务测量后调整。提取、检索、重排、生成、评审及重试共享总截止时间，耗尽时返回可解释状态。

“一次检索”指一次 Adapter 查询调用。mix 内部的图谱/向量分支、关键词模型、重排、embedding、LLM 调用分别记录，不把逻辑检索次数冒充 API 次数或费用。

用于比较路线的判定包括：核心问题覆盖、引用可回查、型号/场景适用、操作条件/否定/等待限制完整、无无依据操作。检索覆盖率和 HTTP 成功不能替代上述判定。无法回答的事实题仅给出“证据不足”，不能算事实回答成功；正确追问或升级在业务动作评测中单独得分。

早期使用人工评审规范与冻结评审记录即可构建首批标签，不要求先完成整个 Self-RAG 系统。自动 Grader 后续用于扩大采集，但其输出需要抽查，争议样本不强制训练。

## 6. Adapter 的实际接口与来源处理

当前代码事实：

- `LightRAG.aquery_data()` 返回 status/message/data/metadata，data 包含 entities、relationships、chunks、references；不生成最终答案，但可能使用关键词、embedding、重排模型。
- `lightrag/utils.py::convert_to_user_format()` 当前只把正文块投影为 reference_id/content/file_path/chunk_id。内部 supporting_chunk_ids、parent_ids、evidence_level 等不会原样全部返回。
- `metadata.retrieval` 保留候选、所选子块、回退和预算信息，`metadata.parent_child` 保留最终来源父块、源子块集合及证据级别。所选候选并不一定全部进入最终正文。
- 来源行可以通过真实 chunk_id 从 text_chunks 获取，父块包属于 full_docs；普通切分可能没有父块、型号范围和页码。

建议首版使用进程内 SDK Adapter，封装公开查询接口和必要的来源读取，保留原始响应，不让业务模块依赖 operate.py 私有结构。工作区和认证仍沿现有服务边界，不开放任意存储访问接口。

统一证据对象至少包含：稳定 evidence_id、返回的实际 content、doc_id、supporting_chunk_ids、primary_parent_id、关联/前置 parent_ids、source_title、pages、带来源的 scope/conditions、evidence_level、原始 reference_id 及 retrieval metadata。引用编号仅在单次响应内有效，跨查询合并不能按 reference_id 去重。

evidence_id 应根据工作区、真实来源集合、证据级别与实际正文指纹确定；普通块同样使用真实来源。父块展开后的正文必须保持展开结果，不以源子块正文替换；metadata 与最终块逐组对齐。多父块证据不能把某个局部范围扩散给整组。

先依据最终 parent_child 元数据关联支持子块，再读取源行补齐来源；普通块按实际 chunk_id 读取。最终证据级别优先使用保留的检索元数据；映射缺失或所有权冲突时明确失败，不能把 20 个候选或 5 个入选子块一概加入答案。

来源字段若在当前接口中确实无法无歧义恢复，应先报告并新增兼容的结构化元数据及回归测试；不得按文件名或内容猜文档 ID/父块。读取来源不等于实施查询硬过滤。

Generator 消费已评价的同一份 evidence bundle。引用指向真实来源，合并后重新生成局部显示编号；不能再无条件调用会重新检索的 aquery_llm()。

## 7. 标签构建与数据文件约定

分开保存三种东西：

1. 业务样本与人工先验：问题、会话、期望动作、候选复杂度、来源、标注理由。
2. 路线实测：每条路线的答案、证据、失败、评审、请求用量与配置指纹。
3. 最终训练导出：仅包含训练输入、经审定的 A/B/C 标签与可审计样本 ID；不含答案或证据正文。

每条业务记录建议字段：sample_id、group_id、input/current_query/confirmed_state、expected_action、candidate_complexity、label_source、label_status、eligible_for_training、manual_rationale。group_id 将同一故障场景、证据事实、同义改写和对话关联起来。

每条路线记录另存：sample_id、route、run_id、system_fingerprint、原始答案、evidence bundle、pass/fail/disputed/not_run、审核人/审核规则版本、错误类型、各类调用与耗时。尚未运行不能填 false，基础设施错误不能当成路线能力失败。

标签生成顺序：

- 先完成风险与信息检查；clarify/escalate 样本进入业务测试集，不作为 A/B/C 训练样本。
- 在允许的路线中，根据合格结果按 A → B → C 选择。B 通过即可确定最小合格路线为 B，不必为了打标签无差别再跑昂贵的 C；完整反事实评估另选子集。
- 设备事实不允许 A。B 未通过且 C 通过，才能形成结果标签 C。
- 三路线全失败、运行未完成或评审有争议时，结果标签为 null；保存排查原因。
- 人工可依据明确证据需求给 B/C 候选先验，始终标注为 provisional。没有实测支持的 C 不叫“只能多步解决”。
- 合并训练样本时优先采用已核实结果，人工先验单独记录、控制比例并做消融。冲突要复核，不重复导出相反标签。
- 原始问题和引用事实不进入被测知识库，训练标签也不能写回知识库。

随文提供 [15 条标注格式样例](../examples/adaptive_router/annotation_examples.jsonl)。它们只用于检查字段、五种动作和讨论边界，均为人工设计、provisional、eligible_for_training=false、route_outcomes={}。其中 B/C 是候选，不是实测金标；不得直接导出训练或宣称数据集已完成。

## 8. 数据规模、划分与防止泄漏

先做 60–100 个独立场景的人工试标，检验标注者是否能一致区分“信息缺失”“缺知识”“单次已足够”和“确需补查询”。这是标注流程验收，不是模型效果验收。

正式数据第一阶段建议收集 600–1000 个原始场景，审核后形成约 300–600 个可用复杂度训练/验证样本，并单独保留业务动作和 unresolved 集合；实际能获得多少 C 应由证据决定，不能人为凑齐。先用 100/200/400 等可用训练规模画学习曲线，再决定是否扩大采集。

按 group_id 先划分，再生成同义改写，推荐训练/验证/盲测按组 70/15/15，尽量分层保留类别。盲测各类样本数不足时报告限制，不宣称统计稳定。正式测试集目标至少 100 个独立场景，含追问、高风险、域外及多轮；达不到时先作为试运行。

三份手册同系列事实高度相似，仅按文档分组也可能泄漏。需要跨文件事实/章节检查和相似问题审核；样本规模允许时增加按型号系列或章节留出的泛化测试，三份资料不能支持广泛设备泛化声明。

现有 30 道检索开发题和 6 道边界题已参与调优，保留作回归，不改名为独立盲测。同一事实的相似样例不得偷偷进入训练。标注格式样例也属于公开开发材料。

## 9. 模型、训练与推理建议

首选 [google/mt5-small](https://huggingface.co/google/mt5-small)：官方模型卡列明覆盖中文，预训练权重需要下游微调。选择它是为了保留 T5 文本到标签的训练形式，并适应中文；不声称一定优于中文编码器。

对照候选 [hfl/chinese-macbert-base](https://huggingface.co/hfl/chinese-macbert-base)：添加三分类头。若它在相同数据划分下质量相当且部署成本更低，可作为后续选择；这是编码器分类方案，不称为原论文同构复现。T5-Large 仅作为原方法参照，首轮不要求重型训练。

先只训练 mT5-small，模型比较在数据流程稳定之后进行，避免同时铺开多个训练任务。下载前记录官方 revision、许可证、权重和 tokenizer 版本；当前尚未下载权重。

训练初值建议：输入最多 512 tokenizer token，有效 batch 16，微 batch 从 1–2 开始，梯度累计；学习率候选 3e-5/1e-4，最多 10 epoch，验证 Macro-F1 连续 2 次无改善早停。种子固定并保存，最终候选尽可能报告 3 个种子的均值和离散程度。这些是中文小数据任务候选配置，不是论文设置。

历史环境有 T4 的记录，但本轮未连接服务器、未确认可用 GPU/显存，也未验证训练耗时和可容纳 batch。训练依赖独立于现有 LightRAG 服务环境，先做少量 batch 的显存与数值稳定性检查。T4 环境优先测试 FP32/FP16，不能假定支持或适合 BF16；非有限 loss 明确失败，不继续保存“成功模型”。

目标文本仍为 A/B/C。新 tokenizer 不一定把标签编码为相同长度，不能直接复制官方代码中取 tokenizer(label).input_ids[0] 的假设。实施时验证 tokenization；可比较三个完整候选标签序列的条件对数似然，再归一化并在验证集校准。验证标签边界、特殊 token 和长度处理，不允许推理自由输出任意 JSON。

输入不能静默截掉当前问题、型号或关键历史步骤。优先保留这些字段，丢弃次要历史时记录截断；核心信息仍超长时明确返回输入限制或追问。训练与在线序列化完全一致。

模型分数低于阈值或前两类分数差过小才触发后备；阈值仅在验证集确定，不先把 0.8 写成可靠概率。记录模型原标签、最终动作、覆盖规则、原因代码和耗时。

## 10. 评测与发布条件

三层分别评测：

| 层次 | 指标与检查 |
| --- | --- |
| 小模型 | Macro-F1、准确率、各类 Precision/Recall、混淆矩阵、校准与后备率 |
| 业务动作 | 五动作混淆、必要追问命中率/多余追问率、明确风险样本升级率、错误 direct 比例 |
| 端到端 | 同一系统下事实正确性、来源支持、型号适用、前提完整、未支持操作、P50/P95、各模型调用量与 token、实际检索次数 |

对照包含固定单步 mix、固定有界多步、简单规则路由和训练模型路由。Oracle 仅从同一版本实测的合格路线中取最简单者作为离线上界，不提供给在线模型。统计总体性能也统计 C、风险、未知范围和多轮等子集；解释质量与费用之间的取舍。

首版候选门槛：独立复杂度集 Macro-F1≥0.85、C 类 Recall≥0.90；冻结的设备事实与高风险检查集中不允许被错误 direct 放行；模拟执行中预算违规和来源伪造为 0。数值为待实测的工程目标，不代表当前能力或所有风险均被覆盖。

端到端正式验收须由用户运行真实模型后完成：相对固定单步基线，整体合格率下降不超过预先约定的 2 个百分点，并改善复杂问题或有实测效率收益；小样本同时给出数量和不确定性。相对固定多步基线应检验是否节约调用与延迟且保持质量。若不满足，模型只离线或影子运行，不自动替换正式入口。

验证集用于调参，盲测一次冻结后才用于最终报告。未运行真实实验时只能报告软件检查，不填模型质量、延迟和费用效果。
