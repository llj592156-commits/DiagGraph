# 十个跳过抽取块的定向补抽

本入口仅处理全量入库清单中的 10 个跳过块，使用原文档、原子块 ID、原父块与当前 printer_v2 合同，不重新解析、切分、抽取其他 1971 个块或重建子块向量。不创建新知识库，也不重新上传三份 PDF。真实 API 由用户运行。

## 运行

在项目根目录预检，后端此时可以保持运行；只读取本地数据并保存冻结计划，不调用模型、不修改知识库：

```powershell
.\examples\parent_blocks\run_printer_skipped_repair.ps1
```

确认 `targeted_chunks=10`、`workspace=learning_paratera`。在后端终端按 Ctrl+C，等待退出，并停止其他同库写入脚本，再执行：

```powershell
.\examples\parent_blocks\run_printer_skipped_repair.ps1 -Run
```

每个尚未修复的块重新请求一次现有抽取模型；仅连接/超时、408/429/5xx 等暂时故障按原入库规则有限重试（每块最多 3 次 HTTP 尝试）。有效响应会在本地保存以供恢复，记录格式仍不合格时保留原跳过状态，继续处理其他目标块。有效空实体/关系数组允许通过，报告的实际实体关系数供进一步审核；格式可用不代表抽出了所有事实。

合格结果使用原有身份转换和图谱合并、来源跟踪与实体/关系向量写入。只有这些新增/合并对象需要 embedding；不调用 Docling、问答、关键词或额外摘要模型。不保证每次都恰好 10 次 HTTP 请求，恢复可能命中保存结果，临时故障可能有限重试。

中断、临时服务错误或部分块仍不合格时，保留输出目录，排查后运行：

```powershell
.\examples\parent_blocks\run_printer_skipped_repair.ps1 -Run -Resume
```

已经完成的块不重新请求或重复合并；有效但未完成入库的响应从本地恢复。已保存的坏响应只在显式 `-Resume` 下重新请求，每次原始尝试均保留。不要删除原报告、原缓存或三份文档来恢复。来源、合同、模型及冻结计划不匹配时明确拒绝，不能通过换目录绕过尚未处理的部分写入。

如果某块在强制 JSON 模式下反复输出空白直至截断，可以显式尝试传输层恢复选项：

```powershell
.\examples\parent_blocks\run_printer_skipped_repair.ps1 -Run -Resume -PlainJsonRetry
```

这个选项仅不发送接口的 `response_format=json_object` 参数，仍使用同一系统提示、完整源块、实体关系合同、原文引用与端点校验。请求文件和本轮汇总记录该选项，不改变冻结的业务合同；输出若仍是坏 JSON 或截断，继续拒绝。它是绕开可能的 JSON 模式生成退化的显式尝试，不保证服务端问题已定位或必然恢复。已完成块和已保存的有效响应不重抽，不自动提高输出上限。保持后端停止。

若已保存的完整响应仅存在 `用于将“保存到 PC"设置为是` 这种中文左引号与未转义英文双引号混用，可运行本地语法恢复：

```powershell
.\examples\parent_blocks\run_printer_skipped_repair.ps1 -Run -Resume -RepairSavedQuotes
```

此选项不调用抽取模型、不补缺失字段、不拼接被截断的 JSON，只在 JSON 字符串内部为明确的混用引号插入转义反斜杠。完整 JSON 解析和全部业务校验仍须通过；不能安全修复时报告失败，绝不自动回退到付费抽取。实体/关系合并入库仍可能调用 embedding。

原始 attempt 响应不变，`syntax_repair_*.json` 另存原响应、派生响应和修改位置；源块修复标记中保存该审计归属。`-RepairSavedQuotes` 与 `-PlainJsonRetry` 不能同时使用。当前真实剩余块的第三次响应离线检查，只需转义两处引号，可接纳 6 个实体和 2 条关系，另 2 条关系仍因端点类型错误被隔离，未经用户执行入库前不算完成。

成功退出后重启后端。只有 `repaired_chunks=10`、`remaining_skipped_chunks=0` 才说明这十个格式/请求缺口都已补完；仍需对新抽取事实做语义检查。

## 保存结果

默认目录为 `outputs/printer_skipped_repair/saved_children_v1/`：

- `plan.json`：来源指纹、型号/身份合同、模型与存储目标，不保存密钥。
- `selected_chunks_before.json`、`cache_rows_before.json`：这十个块原来的失败信息与坏缓存，原始历史不丢失。
- `workspace_before.zip`：运行前整个文件型工作区备份。目录恢复不是自动步骤；勿在后端运行时直接覆盖知识库。
- `request_*.json`、`response_*attempt_*.json`：每次请求与原始响应；按原子块 ID 绑定，不用请求完成顺序猜归属。
- `review_*.json`：原文引用、端点类型、限定条件校验和隔离原因。
- `apply_doc-*.json`：每份文档的候选集合和应用阶段。
- `summary.json`：修复数、剩余块、节点/关系接纳数和本轮调用数。

原全量报告仍记录当时的 10 个跳过块，不回写历史报告。最新状态看本次修复报告及真实 text_chunks。旧 90 题检索结果对应补抽之前的知识库，后续重测要用新的输出目录。

## 来源、提交和恢复契约

程序只接纳当前仍为 skipped 且没有已接纳实体/关系的块；已经由本计划完成或正在发布缓存的块可显式续跑。所有目标须属于 processed 原文档，父块映射完整、合同未变，坏缓存只能有该块一个归属。

在现有 admin 写入门内处理。现有 `merge_nodes_and_edges` 的 Phase 0 是覆盖整份文档候选锚点的语义，不能把 10 块子集传入后覆盖三份文档的旧锚点。补抽先调用原有 `_union_doc_recovery_anchors` 将新候选并入旧锚点并持久化，再禁用合并函数的覆盖阶段；这样已有知识的删除/恢复归属保留，部分新图写入也可被原生按文档清理发现。

先提交并核对图谱、实体/关系向量和 chunk tracking，再发布新的 business_extraction 与原始响应；已有 chunk 缓存引用先持久化，之后以同键替换有独立归属的坏抽取缓存。最后写完成标记，避免下一次恢复继续使用旧坏缓存。来源文本、父子映射和源块向量不改。

接受的失败残留及恢复方式：

- 锚点已并入但图谱未完全落盘：锚点是保守超集，不删除旧归属；错误向外抛出，`apply_*.json` 保留阶段。保持后端停止，显式续跑以保存的同一响应继续合并。
- 部分图谱已提交、块仍标 skipped：不冒充补抽完成；来源仍存在且锚点可达，续跑完成证据发布。底层合并并非跨存储事务，极端中断后的重放可能再次累加边的重要性权重，但来源 ID 会去重；不能将权重当作独立证据次数。
- 新证据已保存、缓存替换或完成标记失败：pending_cache 标记和同一份原始响应支持续跑；不能在此时根据全量 processed 状态宣称修复成功。
- 向量写入失败：明确报错并丢弃可重建的未提交缓冲，保留来源、锚点和响应；不写零向量、不恢复整个旧快照去覆盖其他已落盘数据。

相关底层规则见 [图单写入契约](design/NetworkXSingleWriterContract.md)、[删除恢复契约](design/PurgeRecoveryContract.md)。该入口不是通用的任意子块重抽/替换功能，不支持覆盖已有有效贡献、修改事实或批量修复全部隔离记录。

## 开发验证状态

本轮 11 项定向离线测试通过，覆盖真实文件型存储中的实体/关系入库、原锚点保留、错误 JSON/截断、合法空结果、来源变化与共享缓存拒绝、模型响应复用、图谱中断恢复、缓存发布中断恢复及运行中后端拒绝。新 Python 文件 Ruff 通过，当前 10 块清单的 PowerShell 无 API 预检通过；核对文本块、抽取缓存、图谱及两类恢复锚点文件哈希未变。没有调用真实模型、暂停后端或补写知识库，实际效果以用户运行报告为准。
