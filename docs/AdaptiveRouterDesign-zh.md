# DiagGraph 首版自适应路由设计：LLM 判断

日期：2026-10-19。状态：后端首版与网页入口已接通，用户已运行少量真实单例，尚未完成系统性语义验收。运行方式和明确边界见 [首版使用说明](AssistantV1-zh.md)。

## 1. 当前决策

根据用户最新决定，首版先由高能力 LLM 判断处理策略，后续再接入独立训练的小模型。训练数据规模、GPU、训练脚本和分类器权重不再是首版开发前置条件。

保留五种策略：direct、retrieve_once、diagnose、clarify、escalate。需要检索时首版固定 mix，判断策略与选择 LightRAG 检索模式是两回事。暂缓的型号/场景硬过滤、故障码精确或词法召回继续暂缓。

首版使用结构化提示与程序校验，借鉴 Adaptive-RAG 按问题需求选择检索流程的思想；不能称为已复现论文训练的小分类器。

此前 [小模型训练预研](AdaptiveRouterTrainingDesign-zh.md) 保留为后续参考；当前实施优先级以本文为准。

## 2. 路由工作流

当前问题与必要会话状态 → 明确风险规则 → LLM 一次结构化判断 → 程序校验及业务规则覆盖 → 执行对应策略 → 证据与答案检查。

明确危险优先处理，混合请求不能先处理普通问题而忽视危险。规则覆盖有明确边界，不声称能够穷尽所有风险；LLM 判断及最终输出检查继续保留风险识别。

LLM 在同一次调用中提取型号、故障码及其位置、症状、已执行操作、信息缺口、意图和建议策略，避免为意图、复杂度和槽位分别调用三次模型。每个提取字段保留当前问题/历史用户陈述的来源，模型推断不能直接成为已确认事实。

同一次路由调用还输出 `resolved_query`，将短追问补全为当前可独立理解的检索问题。例如询问过喷嘴检查后，用户问“怎么做”，检索目标应是该型号的喷嘴检查方法。助手历史仅帮助确定话题，不能充当用户已执行步骤或异常结果的事实来源。证据评价、生成和核验同时收到原始对话与 `current_question`，评价当前任务，不要求操作说明顺带解决整个历史故障。未新增独立改写模型阶段。

独立重新生成指令通过 `conversation_context` 定位最近实际用户/助手回合，并跳过独立的重复生成回合；包含新设备或新观察的复合请求仍完整交给模型理解。此前带引用的技术回答不能走 direct 文本改写，须重新解析原业务问题并检索、评价来源。旧助手引用标记仅触发重新核对，不构成可信证据。没有目标历史时澄清；问候和用户原文的纯转换仍可直接处理。五种处理策略和 HTTP 请求字段不变。

历史型号可继承；用户明确换设备时更新。未知信息保持未知，只对会影响检索或建议的关键缺口追问，不机械要求型号、固件和故障码全部齐全。

路由模型只决定初始流程，不承担 Document Grader、故障诊断或最终答案生成。重排分数也不代替证据充分性评价。

## 3. 输入与输出合同

输入包含当前问题、有限会话历史、已确认设备状态、用户已执行步骤和未解决事项。用户内容仅作为待分析数据，不得修改系统路由规则。不输入参考答案或离线标签。

统一接口为 `RouterBackend.decide(request) -> RouteDecision`。首版已经实现 `LLMRouter`，将来可实现 `TrainedRouter`，下游执行器只依赖 RouteDecision。执行边界仍校验替换后端的结果，不允许绕过来源与明确风险控制。

RouteDecision 至少包含：

| 字段 | 含义和约束 |
| --- | --- |
| schema_version | 固定输出版本，未知版本拒绝 |
| intent | 有限业务意图枚举，含 unknown |
| strategy | 五种策略之一 |
| resolved_query | 检索策略的完整当前问题，最多 2000 字符；含历史的检索请求必须提供，保留确认型号及用户不确定性；其他策略使用 null |
| extracted_context | 提取的设备、症状和操作，以及来源；未知值允许为空 |
| missing_fields | 会影响当前问题处理的必要缺口 |
| clarification_question | 需要追问时给出针对问题；不能只输出内部字段名 |
| reason | 一两句决策依据，不要求详细内部推理 |
| risk_flags | 识别的风险类别，供程序与最终检查使用 |

mode、预算、重试和工具权限由执行配置决定，不交给模型任意填写。A/B/C 可由最终策略派生：direct→A、retrieve_once→B、diagnose→C，clarify/escalate→null；不让两套独立输出相互冲突。

执行侧另记 backend、模型/提示版本、输入指纹、请求状态、原始建议策略、最终策略、覆盖原因、耗时和用量。不给模型强制填“置信度 0.95”，也不将其自评当可靠概率。输入、日志和缓存不得包含密钥；会话文本按已有权限边界处理。

程序校验需包括：完整 JSON、严格字段和类型、合法枚举、缺口与追问一致、来源索引真实、策略与意图一致。字符串形式的 JSON 应完整解析，不能截取其中看似可用的片段而忽略截断或额外内容。外部取消继续向上传播。

direct 首版只用于交流、功能介绍及不新增设备事实的用户文本整理。耗材、故障码、设备操作和政策等意图不得 direct。语义判断仍可能出错，规则校验不保证自动识别所有伪装成一般交流的设备事实，须用反例测试并在生成阶段限制无依据事实。

clarify 不能与空缺口、空追问同时出现；risk_flags 与策略冲突时按定义好的风险规则处理。设备事实误选 direct 时不能仅替换字符串就当作有效决策，应记录覆盖并重新校验需要的信息和来源要求。

## 4. 模型配置与失败处理

路由使用可注入的高能力 LLM 调用。当前用户真实请求使用 Qwen3.5-Plus，默认复用 query 角色；本地 `.env` 已按用户要求配置 `QUERY_OPENAI_LLM_EXTRA_BODY='{"enable_thinking": false}'` 请求关闭整个 query 角色的思考模式，需重启生效。已有少量用户实测案例，尚无系统评测；“性能更好”仍需通过冻结样例和真实评测确定，不预设某一模型必胜。

当前核心 ROLES 只有 extract/keyword/query/vlm，没有 router。已实现业务代码允许注入异步调用函数及独立并发/超时配置，HTTP 接口默认在调用时解析现有 query 角色，不使用不存在的 router role，也不将路由逻辑混入 provider 模块。暂未新增 router 环境变量。

支持结构化输出的 provider 优先用其能力，并保留本地严格校验。提示要求简短 JSON 和简要理由，采用较低随机性；参数支持差异通过适配处理，不假定所有厂商支持相同的 response_format 或 temperature。

正常一次路由请求。格式不合格可在同一截止时间内进行至多一次修复请求，保留首次错误；鉴权和配置错误明确失败。暂时服务错误有限重试，修复与网络重试合计最多两次路由请求，不层层叠加。超过上限返回 routing_failed，不伪装成正常回答或模型已选中某路线。

首次真实请求在原 15 秒路由截止时间超时后，首版默认改为路由阶段总预算 60 秒、其他每个模型阶段 60 秒、整个业务请求 300 秒；这些是可调整的等待上限，不是 SLA 或实测延迟。路由重试、检索、重排、生成和评价共享整体截止时间。原小模型预研中的 2 秒不再作为首版 LLM 路由目标。

未来若开启后备路线，必须显式标记 degraded 并单独统计；首批先采用明确失败行为，避免根据缺失的结构化结果猜测是否需要检索或追问。无任何情况可因路由失败而回退到无来源设备回答。

## 5. 五种策略与执行边界

| 策略 | 例子 | 执行 |
| --- | --- | --- |
| direct | “你好，你能做什么？” | 模板或不新增设备事实的回应 |
| retrieve_once | “L4263 的墨水编号是什么？” | 一次 mix，证据检查后基于同一批证据回答 |
| diagnose | “L3251 清洗后仍打印空白，下一步怎么办？” | 先检索；依据证据缺口决定是否补查询，可提前停止 |
| clarify | “应该买哪种墨水？”且无历史型号 | 追问会改变耗材依据的设备型号 |
| escalate | “打印机冒烟并有焦味，还能继续使用吗？” | 风险回应和人工升级建议，不假装实际转接或创建工单 |

diagnose 不是“已经确诊”，也不是必须执行多次。初始路线由 LLM 决定，证据反馈可以让复杂路线提前结束；预算耗尽仍不足则追问、表达不足或升级。

用户实测暴露用户观察问题被误当补查询。当前 `diaggraph-assistant-v1.1` 以证据评价的 `clarification_question` 为停止条件：需要用户描述条纹方向、检查结果等时立即追问；只有缺手册操作、条件或限制时才执行补查。明确已知的操作次数不得重复追问，窄范围规则发现明显违规时要求阶段内修正；这些规则不代替语义评测。模型证据移除定位坐标/跨度/索引计数，仍保留原文和各来源独立适用条件；补查轮优先保留已接纳证据及新增证据，再考虑旧未接纳结果，并按轮记录预算省略，完整 HTTP 来源不变。

首版复杂路线候选预算沿用至多 2 轮、3 次 Adapter 检索：首轮 1 次，第二轮最多 2 个缺口子查询，不固定拆四问。固定单步对照严格只检索一次；生产是否允许单步不足后升级需显式配置和记录，不能混淆两种评测条件。

Adapter 继续保留原文、真实 doc/chunk/parent 来源、范围、前置条件、最终保留证据、实际重排和预算遗漏信息。现有公开块投影不包含全部内部字段，需要结合 metadata 与来源存储读取，不能猜 ID。Generator 消费已审核的同一份证据，不在之后重新执行完整检索问答接口。

## 6. 首版检查与小模型迁移

已有 [15 条格式样例](../examples/adaptive_router/annotation_examples.jsonl) 可作为开发案例起点，不是完整路由基准或实测金标。原 B/C 均是人工候选，允许被证据实测纠正。

软件检查使用模拟 LLM/检索，不调用付费服务；覆盖五种动作、多轮型号继承与切换、缺口针对性、混合风险、误选 direct、截断/坏 JSON、非法枚举、虚构来源、超时/重试/取消及预算。类型和来源无效必须在执行工具前被拒绝。

用户运行真实模型时保存原始路由响应与配置，评估五策略正确率、必要/多余追问、危险请求误放行、端到端答案支持与适用性、P50/P95 和各阶段费用。规则路由、固定单步及有界多步作对照；不能凭 15 条开发样例声称分类质量达到某阈值。

线上日志只产生候选训练材料：LLM 原决策、规则覆盖、最终证据与结果分别记录，人工审核和固定路线实测后才形成训练标签。不得直接将大模型输出视为金标；不能把三路线全失败都标 C，也不能从开发集反复调参后声称盲测效果。

后续小模型仅替换复杂度判断后端时，沿用相同输入和 RouteDecision；信息提取、安全检查等仍由独立组件承担。若小模型只输出 A/B/C，不应假装它同时具备首版 LLM 的完整槽位提取和追问生成能力。迁移时需补齐这些组件并用相同基准做对照。

## 7. 当前实施顺序

1. 新增 `lightrag/assistant/schemas.py`、`retrieval.py` 及对应 `tests/assistant/`，固定证据合同和 SDK Adapter。
2. 新增 `router.py`、`router_prompt.py` 与离线测试，实现可注入 LLM 的五策略结构化判断和严格校验，不等待小模型训练。
3. 增加 `workflow.py`、证据评价和基于同一证据的生成，逐步接通固定单步与有界多步。路由单独测试通过不等于业务闭环完成。
4. 对接独立业务 API 与运行配置，保留现有查询兼容性，再由用户进行真实验证。
5. 流程稳定后积累审定数据，按小模型预研训练和比较独立分类器。

当前已完成上述第 1、2 项及第 3 项的有界后端流程，第 4 项已接入独立 `POST /assistant/query`，网页入口尚未切换。第 5 项训练仍暂缓。本轮只运行离线软件验证与保存记录回放，不调用真实模型、改变服务配置或写知识库；语义效果仍待用户运行验收。
