## 3. 原始业务方案：不能丢失的主线

### 3.1 Adaptive RAG

在查询前识别意图、复杂度、设备信息完整性，动态选择：

- 无需知识检索的通用交流。
- 简单事实问题的单次检索。
- 复杂诊断问题的有界多轮检索。
- 缺型号或关键条件时先追问。
- 业务风险规则要求的升级处理。

`naive / local / global / hybrid / mix` 是可选的检索执行模式；Adaptive RAG 还需要选择是否检索、是否追问、是否补检索，不只是动态改 `mode`。

**不要把方案理解为每个问题固定拆成四个子查询。** 根方案里的四项只是复杂问题的示例。用户已明确纠正过这一误解。

### 3.2 Self-RAG

检索后检查相关性、型号/版本适用性、证据覆盖；不足时在预算内改写并补检索；生成后核对答案是否受到证据支持。

首版是规则与 LLM 组成的评价闭环，不是训练原论文 Reflection Tokens。生成必须消费已经审核的同一批证据，不能评价完后又无条件调用完整问答接口重新检索。

优先用外部业务编排层和公开结构化检索接口实现，必要的核心接入再单独论证。`MAX_SUBQUERIES=4` 等预算是设计示例，尚未成为实现配置。

### 3.3 当前实际优先级

根方案原有 P0 基线、P1 Router、P2 Grader 等阶段。基线测试暴露了资料适用性和结构问题，因此当前增加前置阶段：

## 5. 已发现的问题：不是简单的“文档太相似”

### 5.1 来源存在，但型号约束没有贯穿检索

此前检查发现 A、C 的正文文本块中没有明确 `Lxxxx` 型号标记，B 也只有少量块包含。型号主要出现在文件名；当前块向量主要嵌入 `content`，文件名以独立字段保留。

因此“文件名还在”不等于“召回按型号受约束”。当前 `QueryParam` 也没有已经实现的业务型号过滤字段。新窗口如需实现，须重新核实过滤能否贯穿所有目标模式。

### 5.2 一份手册不代表其中每个段落都适用于全部型号

此前核对 B 手册发现，传真、ADF、以太网等能力涉及 **L5298 专属条件**。因此仅把文件名上的五个型号复制到每个块，仍会把某型号专属功能错误赋给其他型号。

需要区分：文档覆盖型号、章节/段落局部适用范围、显式排除条件、实际型号能力。

### 5.3 固定窗口可能丢失条件与步骤归属

600 token 固定窗口可能分开标题、适用条件、警告、表头、操作步骤，让召回片段看起来相关却缺少必要限制。扩大窗口也可能把不同型号或故障领域混在一起，因此不能只调大 `CHUNK_SIZE`。

### 5.4 图谱合并放大了故障码歧义

此前图谱检查发现 `E-12` 混入网络配置与无边距废墨维护语境，`W-11` 等代码也存在跨手册/操作入口归属混淆。

- B 手册相关操作涉及 `x` 按钮，C 的相关操作涉及 `OK`，不能互相套用。

## 6. 现有解析器和切分器：能复用什么

### 6.1 必须区分的概念

- **PDF 解析器**：提取文字、布局、标题、表格等。
- **OCR**：识别扫描页或图片里的文字，是解析流水线的一项能力。
- **切分器**：将解析产物组织成可索引文本块。
- **父子块检索**：子块索引召回、父块映射和回取的完整机制。

`legacy` 不是 OCR 的别称。当前 PDF legacy 流程主要提取已有文本层，结构保留较弱。Docling 不仅是 OCR 服务，还可以产生结构化解析结果；标题质量需用真实 PDF 验证，不能假定绝对正确。

### 6.2 本项目已有切分策略

| 选择器 | 能力 | 本次方案中的位置 |
| --- | --- | --- |
| F | 固定 token 窗口 | 现有基线；可作为子块对照 |
| R | 递归边界切分，受 token 长度约束 | 优先复用为父块内部的子块切分 |
| V | 利用向量相似度的语义切分 | 可选，涉及额外 embedding 成本 |
| P | 消费 `.blocks.jsonl` 的标题/段落/表格结构并组织块 | 可复用其结构和尺寸处理能力，但不等于父子块系统 |
| C | 自定义回调/插件 | 后续扩展入口之一，需遵守实际注册和调用接口 |

P 缺少结构化 sidecar 时有递归切分回退；不能看到使用 P 就断言标题结构已成功保留。P 本身也会根据大小拆分/合并，因此不能把“P 的每个输出”直接当作完整自然章节。

当前内置 native 路线不是 PDF 结构解析替代品；PDF 的结构化路线重点考虑 Docling，MinerU 为另一已有外部适配器。格式支持以 `parser/registry.py` 的当前实现为准。

## 7. 父子块与适用范围：已讨论方向，尚未实现

### 7.1 父块

父块应代表一个相对完整的知识单元：章节/小节、完整排查流程、表格及必要说明、带条件的操作步骤。

不是机械按一个换行切一个父块，也不是无限长的整章。原则：

- 保留标题路径、步骤顺序、前提条件、警告和来源定位。
- 不跨越互相冲突的型号适用范围或故障语境。
- 过长时继续按子标题、流程或表格结构拆分。
- 表格超长时按行拆分并保留表头，不随意截断单行含义。

### 7.2 子块

在一个父块内部复用 R 或 F 切分，建立稳定 `parent_id`，继承适用范围和来源。任何后续 token 硬限制再拆分也须保留正确父块关系。

此前讨论过父块约 **1200–2500 token**、子块约 **300–600 token**，这些只是试验起点，没有定稿、没有实施，更没有验证最佳参数。

### 7.3 “范围标注”是什么

范围标注描述知识适用于哪些对象和条件，不只是一段父块摘要。例如：

- 文档级覆盖型号。
- 局部章节明确限定的型号。
- 排除型号、功能前提、固件或地区条件。
- 故障码所属领域，例如网络诊断与打印机维护。
- 标注来自文件名、正文明确说明还是人工规则，以及可回溯的原文依据。

优先从显式说明和人工确认规则开始；未知范围应保留为未知，不自动解释为“所有型号通用”。局部条件比文档级候选范围更具体，且不得默默扩大。

### 7.4 建议的数据字段（设计草案）

| 层级 | 候选字段 |
| --- | --- |
| 文档 | `doc_id`、源文件、`document_models`、解析/切分版本 |
| 父块 | `parent_id`、`doc_id`、`heading_path`、内容、页码/源 block 定位、适用范围 |
| 子块 | `chunk_id`、`parent_id`、`doc_id`、内容、顺序、继承范围、源定位 |
| 范围 | `applicable_models`、`excluded_models`、`feature_domain`、`conditions`、范围来源/证据 |

字段名、持久化布局、父块是否单独向量化、图谱抽取使用哪一层，均**尚未定稿**。不要给父块和子块都重复抽取图谱后才考虑重复归属与成本。

### 7.5 检索链路草案

```text
问题中的型号/代码/功能条件
  → 候选召回并执行适用性控制
  → 子块精确命中
  → 找到 parent_id
  → 按范围核验后回取父块相关内容
  → 按父块去重、保留引用、控制 token 预算
  → 生成答案
```

- 不能无条件把每个父块全文加入上下文，造成长度爆炸。
- 跨型号比较题应分别收集每个对象的证据，不按一个型号过滤掉另一方。
- 无型号时按任务追问或保留分型号证据，不静默选择某个型号。
- 只对最终答案做型号检查不够，需要防止错误范围进入召回和图谱证据链。
- 不同检索模式返回的图谱候选、块候选都需要适用性审查；只改 naive 的向量过滤不算完成。

### 9.4 用户最新希望采用的结构

```text
Windows 本地：LightRAG + WebUI + 原始 PDF + 知识库存储
                       |
                 HTTP / SSH 隧道
                       |
服务器：Docling Serve + T4 + Docling 模型
                       |
               返回结构化解析结果
                       |
Windows 本地：sidecar → 切分 → 向量化/图谱 → 检索
```

当前代码已实现 HTTP multipart 上传文件，不要求两端共享 PDF 路径。服务端负责解析，本地接收结果后继续切分和入库。

适配器使用：

- `POST /v1/convert/file/async`
- `GET /v1/status/poll/{task_id}`
- `GET /v1/result/{task_id}`

配置项为 `DOCLING_ENDPOINT`。优先复用用户现有远程连接的端口转发，将服务器 5001 转发到本地一个空闲端口。例如本地选 15001，则本地 `.env` 设置：

```dotenv
DOCLING_ENDPOINT=http://127.0.0.1:15001
```

这里的 `127.0.0.1` 是本地端口转发入口，不是让本地直接访问服务器的回环地址。应先核实实际 SSH/VS Code 转发能力，不编造服务器公网 IP、SSH 端口或开放未鉴权公网服务。

解析成功后才考虑在**实验配置**中使用 `LIGHTRAG_PARSER=pdf:docling-P;*:legacy-F` 等路由。这只选择解析与切分策略，并不实现父子块。现有电子版 PDF 通常不需要强制整页 OCR，`DOCLING_FORCE_OCR` 应经样本验证再设置，不照抄默认 `true`。

Docling 启动配置曾讨论 CUDA、单 worker、限制模型缓存/并发，但未验证当前安装版本全部选项，不要将讨论值冒充已经生效的服务配置。

## 10. 下一窗口建议按这些步骤推进

### 步骤 1：确认新的部署边界

先认可并解释“本地 LightRAG、远程 Docling”可行，主项目不需要继续迁移到服务器。只核实 Docling 哪个环境实际存在、是否能运行、模型是否已经下载；不要继续依赖过期 PID 或残缺副本。

验收：服务器 Docling API 可用，T4 能被该进程使用，本地端口转发可连通。启动和健康检查命令以已安装版本为准。

### 步骤 2：仅解析 B 手册，先不写知识库

优先 B，因为它有一份手册内的型号能力差异。使用整个原始 PDF 或用户允许的样本；用户说过 PDF 不便删减，不把裁剪原文件作为前提。

优先复用 `python -m lightrag.parser.cli ... --engine docling -o ...`，先查看 [docs/ParserDebugCLI-zh.md](./docs/ParserDebugCLI-zh.md)。将输出放到独立实验目录。

检查标题层级、阅读顺序、表格表头、页码/原文定位、型号条件和故障码说明。注意 CLI 对非空 raw 缓存的复用比生产 manifest 验证宽松，测试新解析时要区分缓存与真实请求。

验收：拿出若干真实段落和表格预览，说明结构正确与缺失项，而不是仅报告 HTTP 200 或生成了 JSON。

### 步骤 3：先建立型号目录和适用范围规则

记录文档覆盖型号、章节局部限制、功能能力与故障域，给每条规则附原文依据。先做可解释的人工规则/目录，避免一开始把所有范围判断都交给模型。

验收：可以明确展示 L5298 专属段落如何限制范围，普通段落如何继承，以及未知条件如何表示。

### 步骤 4：实现离线父子块原型

复用结构化 sidecar 和已有 R/F/P 能力，生成父块与子块清单、稳定关联和可读预览。建议暂存 `parents.jsonl / children.jsonl` 等独立产物，文件名和 schema 再定。

验收：子块均可找到父块、不跨冲突范围、步骤和表头完整、长度受控、同文重复内容不覆盖、源位置可追溯。此阶段不调用实体抽取或向量服务。

### 步骤 5：明确检索与图谱契约后，再接入独立知识库

确定父块存储、子块索引、适用性过滤、父块回取/去重/预算、上下文展示、图谱抽取层级和删除重试行为。

先通过最小闭环证明子块召回与父块回取，再逐步验证图谱模式。不得将“naive 改好了”描述为所有模式都支持了型号约束。

新切分会改变 chunk ID、embedding 和图谱来源归属。需要在新 workspace 构建与新 chunk 对应的数据；不是只替换文本块后继续使用旧图谱。旧库保留作对照，不手工删除某几个存储文件。

### 步骤 6：固定条件对照评测

先小样本回归，再覆盖三份资料、跨文档题和边界题。尽可能分别比较：原方案、结构化解析、增加范围标注、父子回取、图谱消歧，避免同时改很多因素后无法归因。

验收：明确哪些错误减少、哪些仍存在、证据是否匹配型号、延迟与成本变化；未确认的结果写成待验证。

### 步骤 7：回到 Adaptive RAG / Self-RAG

基础检索可用后，根据独立评测建立候选路由规则，并实现信息追问、证据适用性检查、有限补检索和答案核验。不要仅依赖题号或原测试题拟合规则。
