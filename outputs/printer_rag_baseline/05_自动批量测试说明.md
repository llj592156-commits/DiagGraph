# 自动批量测试：一次启动，自动收集

工具：`lightrag/evaluation/batch_baseline.py`。只使用 Python 标准库，不用操作网页，也不用安装 RAGAS 或额外评价模型。它调用正在运行的 LightRAG 服务，不启动服务器、不上传资料、不更改知识库。

## 1. 准备

确认三份 PDF 已在目标知识库完成处理，平时使用的服务可以正常查询。下面的命令从 `D:\GitHubCode\LightRAG` 的 PowerShell 运行，默认服务地址为 `http://localhost:9621`。如果端口或 API 前缀不同，增加 `--base-url http://你的地址/实际API前缀`。

默认不读取 `.env`。服务无认证时不需要额外参数。使用 API Key 时，在当前终端通过环境变量 `LIGHTRAG_API_KEY` 提供；已使用其他变量名可以用 `--api-key-env 变量名` 指定。不把密钥写入脚本或结果文件。

如果平时用账号密码登录，在下方命令末尾增加 `--username 你的账号`，程序会隐藏输入密码。无人值守时可通过 `LIGHTRAG_TEST_PASSWORD` 环境变量提供密码。也支持 `LIGHTRAG_TEST_TOKEN` 中已有的 Bearer token；token 失效后需更新，或重新使用用户名登录。

## 2. 先做一次不发请求的计划检查

```powershell
.\.venv\Scripts\python.exe lightrag/evaluation/batch_baseline.py --dataset outputs/printer_rag_baseline/03_题库.jsonl --output outputs/printer_rag_baseline/answer_smoke --ids Q01 Q29 Q30 --modes naive mix --dry-run
```

应该显示 6 个请求。`--dry-run` 不连接服务器、不调用模型、不要求密码，也不创建结果目录。

## 3. 自动收集答案与引用

去掉 `--dry-run` 即可实际运行：

```powershell
.\.venv\Scripts\python.exe lightrag/evaluation/batch_baseline.py --dataset outputs/printer_rag_baseline/03_题库.jsonl --output outputs/printer_rag_baseline/answer_smoke --ids Q01 Q29 Q30 --modes naive mix
```

这会自动执行 3 道题 × 2 种模式，逐条保存答案、引用、引用原文、客户端耗时与请求参数，不需要人工复制答案。默认调用非流式 `POST /query`。只把问题正文和统一查询参数发给服务，不发送题库中的参考答案、原文摘录、评分规则或预设最佳模式。

每次请求开始会输出 `Starting Q01_naive_r1`，尚未收到响应时每 15 秒打印一次等待时长。这只是 HTTP 等待提示，不代表后台模型一定有进展。默认客户端 HTTP socket 超时为 600 秒，可用 `--timeout 秒数` 调整。一次图谱问答可能包含关键词提取、检索与答案生成，而模型接口还可能自行重试；客户端超时不是单个模型调用超时，也不是严格的整个实验总时限。增加客户端等待时间不会提高模型速度。

测试全部 30 道模式对比题、五种模式：

```powershell
.\.venv\Scripts\python.exe lightrag/evaluation/batch_baseline.py --dataset outputs/printer_rag_baseline/03_题库.jsonl --output outputs/printer_rag_baseline/answer_full --question-kind retrieval
```

默认五种模式，共 150 次请求。省略 `--question-kind retrieval` 和 `--ids` 则是全部 36 题，共 180 次请求；`--question-kind boundary` 可单独测试 Q31-Q36，它们不能并入普通有答案题的检索覆盖均分。每次请求独立，不带对话历史。实际运行会产生检索、关键词、生成等正常模型调用费用。

## 4. 单独收集结构化检索证据

如果想观察实体、关系和片段，把阶段改成 `retrieval`，并使用新的输出目录：

```powershell
.\.venv\Scripts\python.exe lightrag/evaluation/batch_baseline.py --dataset outputs/printer_rag_baseline/03_题库.jsonl --output outputs/printer_rag_baseline/retrieval_smoke --ids Q01 Q29 Q30 --modes naive mix --stage retrieval
```

这调用 `POST /query/data`，不生成最终答案，但图谱模式仍可能调用关键词模型。它与 answer 阶段是两次独立检索，不能认为检索结果必然相同。单纯自动收集答案时不必运行两个阶段，answer 阶段已包含同次请求的引用原文；但 `/query` 不暴露原始 chunk_id 与完整实体关系，精查这些字段时才需要 retrieval 阶段。

## 5. 结果在哪里

每个 `--output` 目录包含：

- `report.md`：按题目和模式排列的答案或证据、引用和人工评分空位，直接打开阅读。
- `results.jsonl`：每个任务的最新尝试，方便后续程序分析。
- `summary.json`：各模式成功、无结果、未验证、错误数量，以及成功请求耗时中位数。
- `experiment.json`：题库指纹、问题范围、模式、请求参数、服务地址和实验备注。
- `records/`：每次尝试的完整请求正文、原始响应、状态与耗时。重试保留旧记录。

不要把这些测试结果或参考答案重新上传知识库。`report.md`、`summary.json` 和 `results.jsonl` 是可重建视图，续跑时会更新；正式人工评分应保存在另一个文件中，不直接写入自动报告的空位后指望续跑保留。

## 6. 中断、失败和续跑

按 Ctrl+C 可以中断，已完成请求会保留。使用完全相同的命令和输出目录再次运行，会自动跳过已记录任务，只处理未开始的任务。若请求已被服务器接收但客户端尚未写出记录就中断，该请求可能在续跑时再次执行并产生费用；脚本不保证跨网络的恰好一次执行。

客户端超时或关闭连接后，服务器可能还会继续执行上游模型调用。不要立即多次重启同一批任务；先从服务日志或 `/health` 的模型队列确认上一请求已经结束，再使用 `--retry-errors`。修改客户端 `--timeout` 不改变题目和检索配置，因此可以在原结果目录续跑；早先超时的尝试仍保留其原始记录，新尝试会记录自己的 `http_timeout_seconds`。

失败或未验证任务默认不自动重复。修复服务或认证后，在原命令末尾加 `--retry-errors` 重试它们，保留旧尝试记录。401/403、429 限流、连接失败或超时后会保存当前结果并停止，避免整批重复撞认证或故障服务。429 后应等待服务恢复再续跑。其他已返回的 HTTP/格式错误会被记录，后面的题继续处理。

真实“没有召回结果”与服务故障分开记录。`/query` 在当前版本可能用 HTTP 200 的固定文本掩盖无结果或底层失败，因此 `llm_generated=false` 或缺少该标记时记录为 `unverified`，不能宣称是正常答案或直接等同知识库无依据。必要时检查服务日志或运行 retrieval 阶段定位。

一个输出目录对应固定实验。更改题目、模式、阶段或请求参数时必须换目录，避免混淆。服务端模型、知识库、提示词等变更脚本不能自动识别：请主动换输出目录，并用 `--label` 记录本次模型、知识版本等非敏感备注。同一输出目录只允许一个运行中的脚本进程；不要并发启动相同实验。

## 7. 如何形成模式选择依据

自动化覆盖“提问、切换模式、收集答案、记录耗时和汇总运行状态”。正确性、型号适用性与引用是否支持结论仍需按 `02_参考依据与评分要点.md` 人工核对，当前工具不会用字符串包含关系冒充语义评分，也不会把请求成功率当成答案正确率。

默认统一参数与题库说明一致：`top_k=20`、`chunk_top_k=5`、实体和关系预算各 2000、总预算 8000，关闭 rerank。可通过对应命令行参数调整，但每次对照中保持统一。开启重排用 `--rerank`，服务端需已配置重排器。

使用 `--repeats 3` 可以重复采样；模式顺序按题号和重复轮次轮换，但服务器缓存仍可能影响结果。工具不清除服务器缓存，也不知道真实 token 消耗，相关字段保持 unknown/null。不要把单次热缓存耗时当成某模式的固有性能。

先按每题的原文覆盖、适用性和错误情况比较，再按问题特征分组。允许并列，也允许某题所有模式都不合格。得到候选路由规则后，还需用独立的新题验证。
