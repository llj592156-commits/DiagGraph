# 三份打印机手册：检索模式对比题库

这是一份供人工基线测试的开发题库。共 30 道模式对比题（Q01-Q30）和 6 道信息缺失/证据边界题（Q31-Q36）。未运行实际检索，未给任何题预标“最佳模式”。结果应以当前知识库、解析/分块、抽取质量和参数配置的实测为准。

## 使用方法

1. 确认三份手册均已在待测知识库中完成处理，记录文档名、知识库范围、代码版本、模型配置、解析器、分块与抽取配置。若分开建库，单型号题使用对应库，跨文档题需明确能查询的全部范围；不同模式的范围必须相同。
2. 不要上传本题库、参考答案、JSONL 或测试结果到知识库。它们只能用于测试与评分，否则会泄漏答案。
3. 第一轮先测这 12 题：Q01、Q03、Q06、Q07、Q10、Q15、Q17、Q19、Q21、Q25、Q29、Q30。每题分别运行 naive 和 mix，共 24 次检索。
4. 第二轮 Q01-Q30 分别测试 naive、local、global、hybrid、mix，共 150 次。第一轮结果若设置一致可复用。不要因为某题包含“原因”或“关系”就预设图谱模式胜出。
5. Q31-Q36 单独评价信息缺失、错误前提和无依据处理。它们不并入普通有答案题的召回均分。Q36 必须使用独立请求，不带历史。
6. 每题独立请求、清空对话历史，问题原文保持相同；只改变 mode。不要手动填写关键词，不开启自动路由、问题改写或额外补充检索。
7. 保存每次完整 JSON 结果，建议文件名 Q01_naive_run1.json。先看结构化证据，再看最终答案；两者分开评分。

首轮请求模板（POST /query/data）：

```json
{
  "query": "粘贴下方题目原文",
  "mode": "naive",
  "top_k": 20,
  "chunk_top_k": 5,
  "max_entity_tokens": 2000,
  "max_relation_tokens": 2000,
  "max_total_tokens": 8000,
  "enable_rerank": false,
  "conversation_history": []
}
```

这些参数仅为统一的起始档位，不代表最优配置。top_k 对不同模式选择的对象不同，相同数值不代表相同工作量。总预算保持一致，记录返回实体、关系与片段数量；图谱模式可能把预算用于实体/关系描述。后续单独比较其他档位与重排开关，避免同时改变多项因素。图谱检索可能调用关键词模型；“不生成答案”不代表不使用 LLM。

## 评分与记录

参考评分见单独的参考依据文件。对 Q01-Q30：按参考要点判断原文证据覆盖，0=关键依据缺失，1=仅覆盖部分且缺重要条件，2=覆盖关键事实和适用条件。可同时逐条记录 expected_points 的 covered/partial/missing，以便定位具体缺口。错误型号、错误操作按钮、缺失关键安全前提须单独标记；覆盖高不能抵消这些错误。

引用定位至少记录实际返回的 chunk_id、file_path、reference_id。手册页码用于人工核对，不要求系统返回不存在的页码。实体/关系描述用于寻找线索；关键操作或结论仍须能回到适用原文。正确内容出现在错误型号文档里，不等于完成了型号适用性验证。

对 Q31-Q36：将“是否追问/纠正前提/明确证据边界”和“是否编造结论”分开评分。原始 /query/data 只返回检索数据，不会主动追问，不能据此判定模式失败；要测试回答行为，另用固定生成模型与固定回答要求比较 /query 的结果。

## 如何从结果判断问题特征与模式

- 先逐题比较，再按下方分组汇总平均覆盖和型号/条件错误数；同分时比较不适用内容、耗时与成本。允许并列，允许没有合格模式。
- 失败时先核对正确原文是否成功解析入库、是否分块丢失前提，再检查关键词、图谱抽取和预算截断；不要把所有失败都归因于模式。
- 对准备比较耗时的题，额外重复至少 3 次，交替模式顺序，记录冷/热缓存，使用中位数。少量手工单次结果不能支撑可靠 P95。
- 本题库是开发集。Q01/Q06/Q30 等同一事实族不能拆到训练与测试两边。得到候选路由规则后，应另出新的故障场景作为留出测试；不能用这 36 题既调规则又宣称独立测试提升。
